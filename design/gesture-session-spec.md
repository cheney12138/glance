# 手势与会话 规格

**为什么有这份文件。** 2026-09-17 用户原话:「现在怎么出一个问题修一个, 感觉没有章法, 效率也很低。
是框架你不会用, 还是功能我没描述清楚。为什么做不对呢。要反复修改验证」。

根因**既不是**框架不会用，**也不是**需求没说清：是**一直没有把"输入 × 状态 → 行为"这张表写下来**，
每次只修屏幕上看到的那个现象。"牛皮糖"就是这张表里缺掉的那一格。

**纪律**：以后凡涉及手势 / 会话生命周期，**先改这张表，再改代码**；表里每一格都必须能被
**「一次手测 + 一行日志」**验收 —— 不接受"改了再说""看着差不多"。

---

## 一、一局怎么开始、怎么结束

| 唤起方式 | 打开后 | 结束条件 |
|---|---|---|
| `⌘Tab`（按住不放） | 只在按住时在屏幕上 | **松手** = 生效并关（现状是对的） |
| `⌘Tab` 钉住（设置项）/ **三指轻点** / **四指轻点** | 手指离开触摸板后**仍然留着** | ① `Esc` ② **点面板外**（别的 App 的窗、桌面）③ **点某一格** = 生效并关 ④ **3 秒没动静** ⑤ **别处有键盘/鼠标输入就收**（打字、⌘S、切换 App…） |

**一句话原则**（2026-09-17 用户裁定）：
**用户一旦开始做别的事（点了别的窗 / 按了别的键 / 3 秒没动静），面板立刻收。**
**手指离开触摸板不算"别的事"** —— 那正是"钉住"的定义。

> 病例：「成牛皮糖了」—— 三指/四指唤起后，除了 `Esc` 与点某一格，**没有任何收场条件** ⇒ ④⑤ 缺两格。

## 二、手势判据

| 手势 | 判据 | 动作 |
|---|---|---|
| 三指轻点 | 恰好 3 指 + 按下→抬起 ≤ 300ms + **位移 ≤ 0.03** | 唤起（钉住） |
| 四指轻点 | 恰好 4 指 + 同上 | 唤起 + **直接进未启动环** |
| 四指**按压** | **同帧 4 指**齐压 ≥ 250ms + 位移 ≤ 0.03 → **当场生效**（不必抬手） | 同上（点按失手的兜底） |
| 三/四指**滑** | 同上，但位移**超**阈值 | **什么都不做**（让给系统:调度中心 / App 曝光 / 桌面切换） |

- 手指数按 **max(同帧最大, 去重触点 id 数)** 判卷 —— 前者兜"四指慢落",后者兜"极快轻点从未同帧落齐"。
- **"在板上" = state 1–4**(落板全过程),5–7 才是离板。判卷与位移跟踪的键必须是
  **`identifier`**(每触点唯一流水号) —— 曾经误用 `fingerId`(手内槽位号:拇指 0/食指 1/中指 2…),
  四指同点槽位撞号,去重只剩 2–3 个,是「四指十次唤不醒七次」的全部真相
  (口径对齐 LumaRing `LRContact.id = touches[j].identifier`,MIT)。
- 阈值**用实测定,不猜**。位移阈值演进:无 → 0.08(2026-09-17,治四指滑误唤) →
  **0.03**(2026-09-18,用户实报「操作着操作着就出现了」:三指拖移的**短拖**位移
  0.05–0.08 压线判成轻点;真轻点实测 0.0023–0.0060,0.03 仍有 4 倍余量;
  LumaRing 用 0.025/0.035 同量级,佐证)。实测账每轮进日志(`size=/major=/state=` 字段),
  掌缘豁免线(size ≥4.5 或 major ≥22 不计手指数)据此可继续收紧。
- <30ms 的按压按毛刺丢弃;0.35s 内的第二发判卷按防抖吞掉(防连击反复拆建面板)。
- ⚠️ 代价与边界:位移判据依赖**反推的** `Finger` 结构体布局(`absolute` 字段)。若布局猜错 ⇒
  轻点**永不触发**(可察觉、可回滚)。第一版刻意不看坐标就是为了躲这一点;
  2026-09-17 用户实测「**四指上下滑也会唤出环**」⇒ 这个代价已经付过,换判据。

## 三、没有未启动的 App 时

**环不换、面板不动**，借**托盘那条已有的文字通道**说一句 **「没有未启动的 App」** ——
**1 秒**（2026-09-17 用户裁定:1.2s 太长），**淡入淡出**。

## 四、已知的其它账（写在这里，免得丢）

- 面板**永远相对当前屏幕居中**（上下 + 左右），换环也是 —— 左缘不许钉偏移。
- 换环时**托底不上场**（未启动的 App 只要"上浮"这一层反馈，2026-09-16 裁定）；且不许演出滑走+淡出。
- 换环后 **Tab / ⇧Tab** 在未启动项里移动 —— ❌ ~~不做~~（用户 2026-09-17 裁定 → **2026-09-18 翻案**，见第七节表四：它现在是环的走法本身）。
- `hoverEntry()` 是入口槽时代的**死代码，待清**；`scheduleEntryRevert()` **活着**（`pollLaunchHover` 在用，启动行悬停回退），别误清。
- `design/入口槽-底部形态实验台.html` 里的长条形态已作废（入口改为 `↓` / `↑` 键）。

### 待修 1:入场"上浮"与首帧 alpha 抢跑(2026-09-17 用户实报)

**现象**:「选中即切换的时候, 指向第二个 app, 会有一个上浮动画, 速度加快」。
**机理**(高置信,待改后验证):白光那一招把面板改成 **alpha 0 上屏、下一拍才拉到 1**
(`showPanel`),但入场"上浮"的**起点**仍在 `orderFrontRegardless` **之前**赋值
(`contentEntryRise` / `selectionArmed`)。⇒ 用户**看见**面板时弹簧已跑掉大半,
指针这时进第二格,选中动画从弹簧中段接上去 ⇒ 读作"上浮被加速/一跳"。
**改法**:把"上浮起点"的赋值挪到 **alpha 拉到 1 的那一拍**(即 async 块里),
让**看得见的第一帧**才是入场的第 0 帧。验收:首帧 alpha 修复不退步(白光不回来)+ `[帧]` 无长帧。

### 待修 2:白光在 `681c39f` 又回来了

`5c83d7e` 实测不闪 ⇒ `681c39f` 实测闪。两个提交**单独都编得过**(今天唯一一对干净的二分点),

## 六、排查用的屏蔽开关（不改代码）

「闪光」排查期间：把**未启动环整个关掉**，看它还闪不闪 —— 关掉后 `launchables` 为空，
`↓`/四指都不换环，面板只停在主环。**设置里那一项的真实开关**（不是临时开关）:

```
defaults write com.cheney12138.macswitcher panel.showLaunchables -bool false   # 屏蔽
defaults write com.cheney12138.macswitcher panel.showLaunchables -bool true    # 恢复
```

结论分两种（都要写进 `docs/tasks.md`）：
- **还闪** ⇒ 与未启动环无关 ⇒ 病在**基础面板**（首次上屏那一帧），继续在那边查；
- **不闪** ⇒ 病在**换环路径**（`contentSize` 两套尺寸 / 面板改尺寸那一拍），去那边查。

## 七、双环 = 逻辑一条环，呈现分段换（模型 C，2026-09-18 用户拍板）

**模型**：**逻辑上只有一条环** —— 主环（已启动 App）走完，环的下一段就是未启动段；
**呈现上一次只显示一段**（宽度不叠加，"两套尺寸"裁定原样存活）。
发现性不靠教学、不靠 affordance：**`Tab` 走到底自然遇见**。
`↓`/四指保留为「直达未启动段」的快捷键；`↑` 返回主环。
正式推翻两条旧裁定：2026-09-16「未启动 App 不经 Tab 到达」、本文件落地清单 #4。
推理全程与被否掉的 A/B 两案见 `docs/adr/0013-one-logical-ring-segmented-presentation.md`。

| 输入 × 状态 | 行为 | 验收（一次手测 + 一行日志） |
|---|---|---|
| 主环最后一格 + `Tab`（名单非空） | 进未启动段，**选中接续**到第一格；尺寸/内容同一拍换（实验台 ⑤） | 走到底按 `Tab` ⇒ 段头「未启动的 App · ↑ 返回」出现；`[T91] 段切换(Tab): 主环 → 未启动(选中 [1/N] …)` |
| 未启动段 + `Tab` | 段内下一格；最后一格再按 = 回主环第一格（绕环不断） | 走完未启动段按 `Tab` ⇒ 回主环 `[1/M]`；`[T91] 段切换(Tab): 未启动 → 主环 …` |
| 主环第一格 + `⇧Tab`（名单非空） | 反向进未启动段，选中最后一格 | 主环第一格 `⇧Tab` ⇒ 未启动段 `[N/N]` |
| 未启动段 + `⇧Tab` | 段内上一格；第一格再按 = 回主环最后一格 | … ⇒ 主环 `[M/M]` |
| 任意时刻 `↓` / 四指 | 直达未启动段，**不选中**（与现行一致，`↓` 的语义没变） | 现行路径不退步（现行日志照旧） |
| 未启动段 + `↑` | 回主环，主环选中保持原位 | `↑` ⇒ 主环选中不变；`[T91] 段切换: 未启动 → 主环(↑)` |
| 名单为空 + 主环走到底 `Tab` | 照常绕回主环第一格（段不存在） | App 全启动后 `Tab` 到底 ⇒ 绕回，无段头 |
| 名单为空 + `↓`/四指 | 表三：芯片说一句即散场（现状不变） | 现行验收照旧 |
| 段内 hover | 只挪选中（与主环同一语言）；**误触代价 = 选中挪一格**，不再是"切世界" | 指针扫过 ghost 格 ⇒ 高亮挪一格，托盘纹丝不动 |
| 段内回车(或空格)/点击格子 | 启动并激活，面板散场（现行不变） | 现行验收照旧 |
| 启动成功 | 该 App 下局出现在主环 | 启动后重新唤起 ⇒ 主环里有它 |

**段头**：一行 10pt 小字「未启动的 App · ↑ 返回 / Tab 继续」，住在长条下缘 rowPadY 留白里，
**只在未启动段存在**（主环一个像素都没有）；零高度，不碰尺寸账。

**跨段过渡**(2026-09-18 用户实评「直接闪现太生硬」后追加):窗口宽度与内容用**同一根
0.22s easeInOut** 一起变形;方向随行进 —— `Tab` 内容左滑、`⇧Tab` 右滑、`↓`/`↑` 跳段淡切;
系统「减弱动态效果」时自动瞬时(双边同关)。实验台 ⑤ 的「瞬时改尺寸」裁定保留给
唤起/散场 —— 那两头仍要"已经在/已经没了";跨段行走是环上的高频动作,不在此列。

这个效果定名 **「同根变形」(matched morph)**:两个动画系统(AppKit 动窗框 / SwiftUI 动内容)
**共用同一根曲线、同一段时长**,缩放与替换才读成一次变形而不是两层各动各的。
设计上的正名是 **Container Transform**(Material Design 的模式名),家族叫
**Shared Element Transition**;SwiftUI 对应机制 `matchedGeometryEffect`,Web 底层技巧 FLIP。
查资料/对外交流用正名,仓库内用绰号。复用配方:
① 曲线/时长逐字相同;② 内容侧 identity + transition 做方向性行进(方向跟语义:行走 = 滑,跳转 = 淡切);
③ 减弱动态时双边同关;④ 只用于**状态间的行走**,不用于唤起/散场。
已知成本(2026-09-18 实测):每次跨段约 1–2 帧长帧(60–110ms),P50 不变 ——
窗框动画的逐帧重排,固有、轻微、不累积;嫌重就把 0.22s 收到 0.15–0.18s。

## 轻点 ⌘Tab:不弹面板,直接切(2026-09-22 用户定义)

> 用户原话:「cmd tab 如果只是触发了一次, 就不要展示面板, 直接触发窗口切换。
> 只有 cmd 没松开的时候, 才唤起面板, 然后**显式的定义一下, cmd tab 默认是在 a<->b
> 两个 app 中反复来回切换的**。这样更效率一点, 就不做设置开关了。」

| 动作 | 结果 |
|---|---|
| **轻点**(按下后 ≤0.22s 内松开) | **不弹面板** ⇒ 直接激活"最近用过的上一个 App" ✓ |
| 轻点窗口内**再按一次 Tab** | 弹面板(进入浏览)+ 移动一格 ✓ |
| **按住**超过 0.22s | 弹面板 ✓(之后照旧:Tab/方向浏览、松手确认 ✓) |
| ⇧⌘Tab | 同上一套,方向反向(激活 MRU 里**最久没用**的那个 ✓) |

**显式定义**:正向 = "在**最近两个 App 之间来回**"(A→B、再按 B→A ✓)——
这正是 `唤醒即切换` 的语义;它**关掉**时轻点不适用(那时唤起就是为了看面板 ✓,立刻弹 ✓)。

- 分界 0.22s 是**常量**(用户要求不做开关 ✓):比"有意浏览"的按住明显短、比机械轻点明显长 ✓
- 实现只做一件事:**激活那个 App**(与系统 ⌘Tab 同为 App 级切换 ✓);
  不建面板、不枚举窗口 ⇒ 这就是它快的来源 ✓(窗口级/按屏归属的细腻做法见"接管 ⌘`" ✓)
- Esc / 别处输入等取消路径**不会**再多切一次(取消时状态已离开导航态 ✓)
