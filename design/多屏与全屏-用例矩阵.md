# 多屏 × 全屏 · 用例矩阵(2026-09-19)

背景病例:一块屏全屏播放时,另一块屏普通桌面上的 App 被误判成「无窗应用」灌进两块屏的环
(同一个 App 两屏同时出现、都没有点),主环同时缩水(实测 14 → 2)。
根因与修复见 `WindowEnumerator.rawGroups` 的 T15 判定面收紧(2026-09-19)。

用户裁定:**这类组合行为必须先立用例,再动代码 —— 否则修一个落一个,修一个多一个。**

## 铁律(用户 2026-09-19 口述,全矩阵之上)

> 哪个屏幕的窗口,就应该在哪个屏幕上。**A 屏的 App 出现在 B 屏,绝对不可以。**

1. 单屏全屏:全屏后这块屏就只有全屏 App(如 Chrome)—— 符合预期;要看到别的 App 就退全屏。
2. 一屏全屏、一屏非全屏:**绝不**把全屏那块屏的 App 塞到非全屏屏的环里 —— 它本来就不在那块屏显示。
3. 双屏同时全屏:两块屏的环各自只有各自的全屏 App(如腾讯视频全屏 = 只有腾讯视频)—— 符合预期。

## 前提变量

| 变量 | 取值 |
|---|---|
| 「显示器拥有单独 Spaces」(系统设置) | 开 / 关 |
| 哪块屏有全屏窗 | 无 / A / B / A+B 同时 |
| 语境屏(唤起面板的那块屏) | A / B |

> 「单独 Spaces」**关** = 全局共用一个 Space:一块屏进全屏,**所有屏**的普通桌面都被盖住
> (macOS 自己的世界模型,不是本 App 的选择)。**开** = 每块屏独立 Space,互不影响。

## 用例矩阵

| # | 场景 | 预期 | 状态 |
|---|---|---|---|
| F1 | 单屏,无全屏窗 | 环 = 本屏可见窗;真·无窗应用(全量清单任何地方都没窗)追加在列 | ✅ 现行 |
| F2 | 单屏,本屏 App 全屏,在本屏唤起 | 环 = 全屏 App(它是本屏唯一可见的 layer 0 窗);其它 App 的窗在别的 Space,不出现、也不算无窗 | ✅ 现行(用户实测:只剩 Chrome,2026-09-19) |
| F3 | 双屏 + 单独 Spaces **开**,B 全屏,在 A 唤起 | A 环**照常**(A 的窗不受 B 影响);B 的全屏窗归 B | ✅ 语义如此(待双屏实测) |
| F4 | 双屏 + 单独 Spaces **关**,B 全屏,在 A 唤起 | macOS 语义:全局 Space 切到 B 的全屏,A 上没有可见窗。**B 屏的 App 绝不许出现在 A 的环里**(铁律 2)。现行:A 环无窗 → 面板不出现(「本屏无窗」),维持 | ✅ 现行(2026-09-19 T15 收紧后成立) |

| F6 | 全屏进出**瞬间**唤起(窗口集体离屏/回屏的过渡期) | 环成员 = 当次枚举结果;T15 善后期(10s)挡住"刚失去窗的 App 诈尸";**不得**出现无点条目灌环 | ✅ 现行(T15 判定面 2026-09-19 收紧) |
| F7 | 只剩最小化窗的 App | 全量清单里有窗 = **不算**无窗 → 不出现在环(代价,用户裁定接受 2026-09-19:唤起场景本来就不显示最小化窗的卡片) | ✅ 现行 |

## 不变量(任何用例下都成立)

1. **按屏归属**(ADR-0008 铁律):一扇窗只出现在一块屏的环里;跨屏候选集不存在。
2. **无窗应用判定面 = 全量窗清单**(含其它 Space、最小化):只要任何地方还有 layer 0 窗,就不是无窗应用。
3. **无点条目只能来自真·无窗应用**(T15 语义),不得由 Space 切换、全屏过渡批量制造。
4. 环成员数在稳态下应当**可复现**:同一桌面状态连唤两次,数量一致(病例:2 vs 14 对不上)。

## 验证方法

- 单屏 F1/F2:本机即可(全屏 Chrome/视频,唤起,数环成员)。
- F3~F5:需要双屏机器(另一台开发机),`defaults write com.cheney12138.macswitcher debug.trace -bool true`
  后看 `~/Library/Logs/Glance/trace.log` 的 `[T6] 落点顺序` / `[唤起] N 个 App` 行。
- F6:全屏退出的 1s 内连续唤起三次,环数量应当一致地递变,无诈尸。
