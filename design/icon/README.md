# Glance 图标(设计源 + 再生成)

两个标记,一个来源:

| 标记 | 落点 | 说明 |
|---|---|---|
| **App 图标** | `Sources/Glance/Assets.xcassets/AppIcon.appiconset` | macOS 十档 16…1024,每档从矢量直接栅格化 |
| **菜单栏图标** | `Sources/Glance/Assets.xcassets/MenuBarIcon.imageset` | 18/36/54(1x/2x/3x),`template` 渲染 |

## 设计读(read)

**Glance = 光透过玻璃**(与设置窗那句"glance 是关于光透过玻璃的名字"同源)。
面板的实物就是一块玻璃长条、三条窗格、中间一格被选中 —— App 图标是它的正投影:

- 深底 squircle,是"桌面在玻璃后面"
- 长条里那束蓝→紫→青,是透进来的光;**棱镜色散边**沿长条顶缘走一道,是全图唯一一次光谱色
- 三格窗:中间那格更亮、更大,套**聚焦蓝**双环 —— 选中,不是装饰
- 全图彩色只有两源:聚焦蓝 + 那道棱镜(红绿灯不在图标里出现)

度量:1024 画布,squircle 内容 **824**(= Apple 80.5% 安全区,与 `AppIconProvider`
量别人图标时的口径同源),超椭圆指数 n=5 逼近连续圆角。

**菜单栏图标是它的简化变体**:同一根长条、同样三格、同样"中间更大"。
没有玻璃、没有色 —— 菜单栏不需要第二套语言。

## 为什么菜单栏图标"必须是白色"

菜单栏图标正确的做法是 **template image**:只画形状(alpha),颜色由系统给 ——
深色菜单栏上渲染成白,浅色菜单栏上渲染成黑。

所以资产里存的就是**纯白形状 + 透明底**,`Contents.json` 里声明
`"template-rendering-intent": "template"`;系统据此在浅色栏上自动变黑。
若强写死白色,浅色菜单栏上就是一个看不见的图标。

接线在 `Sources/Glance/App/GlanceApp.swift`:
权限齐 → `Image("MenuBarIcon")`(asset catalog);缺权 → `Image(systemName: "exclamationmark.triangle")`(SF Symbols)。

★ **两格必须是两个构造器,不能合并成三元表达式**:`Image(_ name:)` 只查 asset catalog,
`Image(systemName:)` 只查 SF Symbols。合并写法(曾经就是这么写的)会把 SF Symbol 名喂给
asset catalog,查不到就画一个空图 —— 日志里报 “No image named 'exclamationmark.triangle'
found in asset catalog”,而菜单栏上“缺权限”整个没有可见信号。

## App 图标:定稿(2026-09-15)

**来源 = 外部生图模型出的那张正投影**(`glance-source.png`,2048×2048,暖米色渐变底)——
不是矢量的。所以这份资产的性质是:**一张被精确裁切过的位图**,不是"可无限缩放的矢量"。

裁切是**确定性**的,由 `Tools/Iconify.swift` 一次跑完(不手改 PNG):

```bash
swiftc -O -target arm64-apple-macos14.0 -o /tmp/iconify Tools/Iconify.swift
/tmp/iconify design/icon/glance-source.png      # 出 icon/icon_{16…1024}.png + 预览
```

四步,每一步都有理由(踩过的坑写在注释里):

1. **找边从外向内扫"第一条跳变"**,不是找"最强边" —— 中线竖扫时最强的那条是里面那层磨砂头,
   玻璃外壳的顶边是柔和渐变、强度反而低 ✗;
2. **强制正方形**(用宽度同时当高)—— 底边扫到的是投影会偏大,照它裁会把图形拉长 ✗;
3. **再内缩 2.00%** —— 从外向内扫到的第一条边是外层**泛光**的起点,不收就会带出一圈背景光 ✗。
   这个数字是**量出来的**:沿四条边取样比较"本地背景色",顶边到 1.75% 才干净(1.6% 时还有 12% 的
   样本是背景 —— 就是当初肉眼看到的那一点点 ✗)。判据只用顶边,因为另外三条边的玻璃本身近似背景色、
   这个指标会误报(注释里写明了,免得后人拿那三个数做决策);
4. **圆角遮罩 31.5%** + 摆到画布 **82%**(Apple 图标网格),四周透明 —— 生成图的水印在方块外,自动切掉 ✓。

写回资产目录:十档按 `Contents.json` 的槽位命名(16/32 各 1x·2x …… 512 各 1x·2x)。

**已知局限**:位图降采样到 16/32px 是干净的,但它**不是矢量** —— 真要无限锐利,得由设计同学
**分层描摹**成 4 条路径(外壳 / 头 / 三块)。

## 坑五:米色边框(2026-09-15,用户报"app 图标的边没清理干净")

**症状**:导出的图标里,圆角方块的左边、右边、下边各贴着一条**很淡的米色描边** ✗ —— 正是源图的底色
`#F1EDE2` 被一起裁了进来。顶边却没有 ✓。

**量法**(探针沿四条中线往里走,统计"暖色背景像素"的带宽,源图底色是暖的、玻璃是绿灰的,判据分得开):

| | 左 | 右 | 上 | 下 |
|---|---|---|---|---|
| 修前 | **1.76%** ✗ | **1.76%** ✗ | 0.00% ✓ | **1.17%** ✗ |
| 只改锚点后 | 0 ✓ | 0 ✓ | 0 ✓ | **1.17%** ✗ |
| 再收内缩到 1.8% | 0 ✓ | 0 ✓ | 0 ✓ | **0.39%**(2px @512,肉眼不可见) |

**根因(两个叠加)**:
1. `side0 = max(宽, 高)` 想修"顶边被切",但**底边扫到的是投影**、天然偏大 ✗ ⇒ 方框被撑大;
   而外接方是**居中**放的 ⇒ 多出来的尺寸**左右各溢出 ~1.8%** ⇒ 米色底进了画面。
   顶边干净恰好是证据:**上边扫到的才是玻璃自己的边** ✓。
2. 四条扫描线都先扫到玻璃**外面那层柔光** ⇒ bbox 天生比玻璃本体大一圈,遮罩自带的 0.4% 内缩
   只够吸收左右两侧,吸收不了多出来的下边。

**改法**:边长回到**宽度**(水平中线不扫投影,可信) + 以左上为锚 + 内缩 **0.8% → 1.8%**
(与 82% 时代那段扫描得出的 1.75% 互相印证 —— 两次独立测量同一个量级)。

**纪律**:这类"边缘脏"不要靠眼睛调参 ✗ —— 写个探针把"脏带有多宽"打成百分比,
改完再打一次,数字说了算 ✓。(探针思路:从画布外往里走,找"第一个不透明像素"和"最后一个暖色像素",
两者之差就是脏带。)

## 坑六:渲染自带柔边 —— 该换的不是裁切,是那张图(2026-09-15,用户报"github 里 README 的 icon 还是有米色边")

**先说结论**:这一圈不是抠图残留,是**渲染本身**的 —— 半透明玻璃 + 暖调 + 边缘柔光,
在 README 的 112px 下就呈现为"贴着边的浅色圈"。裁切只能把它**挪**走,不能消灭它。

**过程(记下来,因为中途我判断错过两次)**:
1. 探针(沿中线量"暖色像素带宽")在四条中线上**已经是 0** ✓ —— 于是我先怀疑是 CDN 缓存;
   对比 raw.githubusercontent 的字节 ⇒ **完全一致** ✓,排除缓存。
2. 于是把探针扩到八条线(四边 + 四角)。**这个读数不可信** ✗:左上角永远是 75–83px,
   换任何参数都不动 —— 因为那条对角线穿过的是**渲染自己的暖色受光区**,不是脏带。
   教训:**探针的判据要能区分"脏"和"画面本来就这样"**,否则它会给出看似精确的假信号。
3. 真正把问题定住的是**并排对照**:把图标缩到 README 的实际显示尺寸(112px),
   和一张**原生图标**(Ghostty,同一台机器、同一底色、同样缩放)放在一起看 ✓。
   一眼就看出来了:不是"多了米色",而是**整体偏米、边界软**。

**改法**:内缩 1.8% → 3.0%,遮罩圆角 0.29 → 0.305(都做成了参数,可扫参)。
下边/右下角的残留归零 ✓,代价是方块小约 1.2% ✓。

**方法论(比这次的具体数值重要)**:
- 判"边缘干不干净",**同尺寸 + 同底色 + 有原生基线**的并排图,比任何像素指标都可靠 ✓;
- 像素指标要先证明它能区分"缺陷"和"风格" ✓,否则它只是把噪声写成百分比 ✗;
- 两次独立测量(1.75% / 1.8%)互相印证过,依然可能**量错了对象** ✗ —— 印证不等于正确。

### 坑六 · 补充(同一天,我改坏了一次 —— 用户报"左上角给我改的脏脏的")

上一轮我按 A 方案把内缩收到 **3.0%**,并宣布"更干净" —— **错了** ✗。
在 1024 下看左上角:出现**一块灰斑 + 一条硬斜边**,原因是内缩过大之后
(a) 图标被整体放大,(b) 遮罩的边界正好**切过渲染自己的角落阴影** ✗。

**我为什么会判断错**:我是拿 **112px 缩略图**看的 ✓ —— 那个尺寸下角落细节根本不存在,
我只看到了"边缘余辉变少"这一个维度。

**最终取值**:内缩 **2.2%** + 圆角 **0.29**(与玻璃自己的弧一致)。
取舍是量出来的:1.8%(T73)角落干净但边缘余辉留得多;3.0% 边缘更净但角落脏;
2.2% 两头都不越界 ✓。

**再加一条纪律**(与坑六正文同源,但方向相反):
- 判"整体观感"→ 缩到**实际显示尺寸**(README 是 112px)看 ✓;
- 判"角落/边缘干不干净"→ **必须放大到 1024 看局部** ✓。
  两个尺寸看的是**不同的东西**,不能互相替代 ✗。

另附一个容易骗过自己的现象:改了图标后 **Dock 里显示的还是缓存** ✗
(所以"本地 app 图标没事"很可能是它 —— 退出重开或 `killall Dock` 才刷新)。

### 坑七:探针的判据漏了"白色"(2026-09-15,用户报"上下左右四个角的白边没裁干净")

换成蓝版新图之后,我的八条线探针报"脏带全 0" ✓,但用户一眼就看出**四角有白边** ✗。

**为什么探针看不见**:它的判据是"**暖色**像素"(R−B>9,为的是抓旧图的米色底 #F1EDE2) ——
而新图的背景是**纯白**,白是**中性色**,过不了暖色判据 ✗。
一个为特定病例调的判据,换一张图就失明了 —— 而且它**照样输出"0"**,看起来更可信 ✗。

**新判据**(加到同一把尺里):近白 = alpha≥250 且 RGB 三通道都 ≥246
(方块内部最亮处约 240 出头,所以这个阈值分得开)。统计**四个角各 18% 边长的方区**里的近白像素数。

**量出来的结果**:
    圆角 0.22 → 四角近白 **631** 个 ✗(就是用户看到的白边)
    圆角 0.24 → **0** ✓(再大也是 0)
⇒ 取能切干净的最小值 0.24,尽量少改用户自己设计的弧度 ✓。

**纪律**:
1. 判据要**正反两面都量**:"有没有脏"和"有没有残留",前者是出现、后者是遗漏,一个阈值测不了两件事;
2. 换素材(新图/新渲染)**必须重跑一遍全部探针**,并检查每个判据是否仍适用于**新图的配色** ✗;
3. 拿到"全 0"先别高兴 —— 先问一句:**这个 0 是"干净",还是"没看见"?**
