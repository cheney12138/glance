# 预览托盘 · 功能铁律

> 这份文档回答一个问题:**如果重来一次,该立哪几条规矩,才能让这一整族问题不出现在代码里。**
> 每条铁律都附上**它是被哪一次事故逼出来的** —— 没有事故的那几条,是设计推演,会标「推演」。
>
> 适用对象:预览托盘(卡片行 + 芯片 + 玻璃 + 落位)以及任何"实时画面"类视图。
> 最后更新:2026-09-21

---

## 一、数据与来源

### 铁律 1:一个属性只能有一个来源
**同一件事(几何 / 裁切 / 采样率 / 取数来源 / 内容框 / 缩放),全链路只能有一个来源。**
两个来源必然在不同时刻漂,而漂的表现永远是"看起来像 bug 的现象"。
> 事故:快照链与 live 链各算一套裁切/比例 ⇒ "换源那一刻画面移了一下"(实测比例差最大 13%)。
> 后来还顺带发现:尺寸账、排布、命中判定三处各算一套宽度 ⇒ 托盘出屏。

### 铁律 2:能用一个源,就不要用两个源
第一版就选"单一管线";"两个源互为补充"永远会变成"两个源互相污染"。
> 推演 + 事故:live 开启时**整条快照链退出展示**(不进采集、不进绘制、不被依赖),
> 而不是"哪个新用哪个"。

### 铁律 3:量具不得改变被测物
任何诊断 / 探针 **默认关**、**不进渲染路径**、**不得与被测路径共享时序资源**。
> 事故:上屏像素探针一开,就稳定产出 70–190ms 的长帧 ⇒ 我拿它去量"掉帧",
> 量到的其实是它自己 ✗(见 `docs/live-preview-设计.md` 附录)。

## 二、尺寸与位置(这一族最贵)

### 铁律 4:一局之内,尺寸只在开局算一次
窗口尺寸是**一局的不变量**(ADR-0006);凡是"跟着内容走"的尺寸(卡片/托盘/行高),
必须在开局**冻结**,局中不许重算。
> 事故:`frozenSize` 只写不清,且没人监听显示配置变化 ⇒ 接拔外接屏后一直用旧规格,
> **一直错到 App 重启** ✗。

### 铁律 5:位置不能是"内容宽度"的函数 —— 设计阶段就要选定
如果行是**紧排序列**,那么第 k 张卡的左缘 = Σ(前 k−1 张宽度) ⇒
**内容一变,位置必变**。"位置不动" ⟺ "占宽固定";"形状跟内容走" ⟺ "占宽随内容" ⇒
这两句**逻辑互斥**,必须在设计阶段做取舍并写进 ADR,而不是事后靠调参补救。
> 事故:ADR-0014。试过三条路(固定槽位 / 统一卡面 / 同图模糊铺底)全部被实评否决,
> 最终裁定"保留形状、接受位移",并把减痛措施写清(左锚定 / 组内不动 / 可预测)。

### 铁律 6:锚定只能用"固定边",不许用"居中"
居中会把**宽度的任何变化**翻译成**位置的变化**;固定边(左/上)只让"远端"伸缩。
> 事故:内容在托盘里居中 ⇒ 换组时整块平移 200–300pt ✗(日志 `[对位]` 直接读数)。

### 铁律 7:视觉层与几何层分离
玻璃 / 阴影 / 圆角 / 受光边属于**可见层**,可以随意增删;
**尺寸账不许跟着它走**(增删视觉层时,窗口大小与位置应保持完全一致)。
> 事故:撤掉托盘外层玻璃时,只动视觉层、几何口径原样保留 ⇒ 一次就过。

## 三、环境与归属

### 铁律 8:一切像素与坐标必须"按屏归属"(ADR-0008)
禁止 `NSScreen.main` —— 它 = **有 key window 的那块屏**,而浮层永不成为 key。
scale / 可用区 / 刷新率 一律取"**该元素所在的那块屏**"。
> 事故:三处像素换算用了 `NSScreen.main` ⇒ 双屏时取到另一块屏的比例(差一倍)。

### 铁律 9:环境一变,整局作废
显示配置(接拔屏 / 改分辨率 / 换主屏)、权限、系统缩放变化 ⇒ **全部作废重建**:
停采集 + 清冻结规格 + 清图缓存。不允许"增量修补"。
> 事故:同上。监听 `didChangeScreenParametersNotification` ⇒ 换屏 = 换一局。

## 四、浮起来的东西要自己站住

### 铁律 10:任何"脱离容器还能漂浮"的元素,必须自带足够的底
不许假设"下面一定有玻璃 / 一定有浅色背景"。
文字所在的那一层必须**自己保证对比度**(深底浅字或浅底深字,且不透明度足够)。
> 事故:托盘外层玻璃撤掉后,芯片直接坐在任意背景上 ——
> 浅色 `white .26` / 深色 `slate α .40` 都等于没底,浅字被背后的亮码冲淡 ✗。
> 修法:两格都提到 α .7x + 一根可辨的发丝边 + 极淡投影。

### 铁律 11:卡面尺寸(布局)与图像铺法(内容)是两个决定
分开写、分开调。混在一处时,改一个必然坏另一个。
> 事故:"统一卡面"改的是布局,"fill/fit"改的是内容 —— 混着改了三轮,
> 每轮都只坏一半,读日志都读不出来。

### 铁律 12:容器的尺寸由**记录**决定,不由内容决定
内容(截图 / 实时帧 / 静默态 / 文案)只能**填充**容器,不许反过来撑大或缩小容器。
> 事故:卡片宽度一度由"图的比例"推 ⇒ 换源时卡片自身改宽 ✗。

## 五、性能与清理

### 铁律 13:每帧路径里不许有重活
模糊 / 缩放 / 解码 / 系统查询 / 枚举 一律**后台算一次 + 缓存**,
且缓存必须能被"环境变化"统一清掉。
> 事故:高斯模糊写在渲染路径里 ⇒ 换选中 12–24ms;卡片底图每次重建 ⇒ 10–27ms;
> `orderFrontRegardless()` 每次 hover 都调 ⇒ 4–35ms。

### 铁律 14:每个状态都必须有"归零路径",且由**同一个类**保管
不变量状态的**建立与撤销写在一起**(如 `place()` / `setContentHidden()` / `teardown()`),
让"忘记配对"在结构上不可能发生。
> 事故:手写的 `trayOnScreen` 没有配对 ⇒ 托盘再也不出现 ✗。

### 铁律 15:手感 / 时机类问题,先有量尺再动手
没有能量出数字的尺子时**不许猜**;尺子要廉价、可常开(如 `[对位]` / `[悬停拍]`),
重型诊断另开关且默认关。
> 事故:第一轮我用"悬停后那几拍"当样本,得出"12/12 都紧跟 hover" —— 那是把筛选条件
> 写进了结论 ✗。正确做法:对每次异常,回看前后 ±80ms 的**全部**日志。

## 附:这一族问题的诊断顺序(照这个顺序查,不会绕远)

```
1. 位置/尺寸不对?
   → 先看"这一个数是谁算的"(唯一来源?冻结?)
   → 再看"它跟内容走还是跟记录走"
2. 只在某些环境出现?
   → 按屏归属 / 环境变化作废 这两条先过一遍
3. "感觉卡"?
   → 先量帧间隔,再分层(后台工作 / 渲染路径 / 采集成本)
   → 确认量具本身不产生这个现象
4. "看着不对"?
   → 先分开"哪一层在动":容器 / 内容 / 可见层
```
