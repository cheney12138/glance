# 掉帧排查 · 现状（2026-09-21）

> 用户报的症状：「tab 切换到大象的时候，出现了**上浮掉帧**」/「明显掉帧，我是确定的」。
> 这份文件只写**已经量到的事实**和**下一步砍哪儿**，不写推测当作结论。

## 一、已经**证明清白**的（有数据）

| 结论 | 证据 |
|---|---|
| **我们自己的代码每次 Tab < 2ms** | `traceCost` 的打印阈值就是 2ms；两个会话 **98 次 + 20 次 Tab，`[工] 键盘换选中` 一行都没打** ⇒ 全部低于阈值 ✓ |
| 托盘的更新极便宜 | `[工] ↳托盘更新 主线程 0.1–0.6ms` |
| 那个「上屏像素探针」不是元凶（但会改变被测物） | `debug.screenProbe` 一开自己产出 70–190ms 长帧 |
| 导图探针在吃实打实的一块 | `debug.dumpSources` 关掉前后：**max 帧 45.4ms → 28–37ms**、长帧 39 条 → 1–6 条 |
| 「只派可见组的帧」有效 | 改前长帧里 6/9 带「直播新帧 ≥1」；改后基本全是「直播新帧 0」 |
| 不是图标的选中投影 | 消元开关两趟对照：长帧 2 条 vs 1 条 ⇒ 噪声级 |

⇒ 所以剩下的长帧（**偶发 1 帧，20–33ms**，落在"换选中那一拍"）**不是我们的代码**，
是 **SwiftUI 提交 + 那一扇大窗（1758×374，2.6M px）的重绘**。

## 二、量具自己翻过的车（都记下来，别再犯）

1. **改变被测物**：`screenProbe` 自己产出 70–190ms 长帧；
2. **读错顺序**：日志有多路写入者，`grep` 出来的行序**不是时间序** ⇒ 必须按时间戳排序
   （`awk` 取时间戳 + `sort -n`，命令在 `docs/量尺代价表.md`）；
3. **计数跨拍累积**：`直播新帧 8` 是攒出来的（10fps 的窗不可能一拍交 8 张）⇒ 已改成每拍取走；
4. **打点打在错的路径上**：`lastHoverMark` 只在指针 hover 打点，而用户的复现是**键盘 Tab**
   ⇒ 前几轮量到的长帧全是指针那一路，**没覆盖用户报的那一下** ⇒ 已补 `moveApp` / 窗口选中；
5. **旧构建在屏幕上**：用户按了 55 次 Tab，日志里新加的计时器 0 行 ⇒ 那个进程没有新代码。
   ⇒ 已补 `Tools/run.sh`：**停干净 → 起新构建 → 自证"进程启动晚于二进制 mtime"**。

## 三、下一步砍哪儿（两个候选，都还没验完）

```
候选 A：长条自己的大投影 `.elevation(.strip)`
   它在 1758×374 的圆角矩形上做离屏光栅化 ⇒ 每次内容变化可能整层重画 ✗
   临时开关:`debug.noStripShadow`(已加、已进重型清单、开机自报 ✓、验完删)
   对照方式:粘 `defaults write com.cheney12138.macswitcher debug.noStripShadow -bool true`
           ⇒ 同样动作(唤起 → Tab 到大象 → 关面板)⇒ 比长帧条数

候选 B：长条那层玻璃(NSVisualEffectView 系)
   若 A 否掉 ⇒ 下一个消元对象；再不行就看"是不是整窗合成"这条底账。

若两者都否掉 ⇒ 剩下的路是**结构性**:把"上浮 + 换选中"这一拍的重绘面积变小
   (例如上浮改走 CA 层动画，不让 SwiftUI 逐帧重画整窗)。
```

## 四、这一轮顺带落下的东西（都在 `refactor/decouple-design-entry-points` 分支上）

- `FrameProbe`：每拍取走"直播新帧"计数 + 键盘路径补打点；
- `LivePreviewPool`：**只把当前显示组的帧交给主线程** + 换回来时补一帧；
- `docs/量尺代价表.md`（四档量尺 + 两条事故 + 三条规矩 + 排序命令）；
- `DebugFlags.heavySwitches` + 开机自报（重型开关不允许静默开着）；
- `Tools/run.sh`（干净重启 + 自证新构建上屏）；
- 临时件（**验完要删**）：`debug.noStripShadow`。
