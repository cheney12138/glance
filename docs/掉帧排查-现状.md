# 掉帧排查 · 现状（2026-09-21）

> 用户报的症状：「tab 切换到大象的时候，出现了**上浮掉帧**」/「明显掉帧，我是确定的」。
> 这份文件只写**已经量到的事实**和**下一步砍哪儿**，不写推测当作结论。

## 一、已经**证明清白**的（有数据）

| 结论 | 证据 |
|---|---|
| **我们自己的代码每次 Tab < 2ms** | `traceCost` 的打印阈值就是 2ms；两个会话 **98 次 + 20 次 Tab，`[工] 键盘换选中` 一行都没打** ⇒ 全部低于阈值 ✓ |
| 托盘的更新极便宜 | `[工] ↳托盘更新 主线程 0.1–0.6ms` |
| 那个「上屏像素探针」不是元凶（但会改变被测物） | `debug.screenProbe` 一开自己产出 70–190ms 长帧 |
| 导图探针在吃实打实的一块 | `debug.dumpSources` 关掉前后：**max 帧 45.4ms → 28–37ms**、长帧 39 条 → 1–6 条 |
| 「只派可见组的帧」有效 | 改前长帧里 6/9 带「直播新帧 ≥1」；改后基本全是「直播新帧 0」 |
| 不是图标的选中投影 | 消元开关两趟对照：长帧 2 条 vs 1 条 ⇒ 噪声级 |

⇒ 所以剩下的长帧（**偶发 1 帧，20–33ms**，落在"换选中那一拍"）**不是我们的代码**，
是 **SwiftUI 提交 + 那一扇大窗（1758×374，2.6M px）的重绘**。

## 二、量具自己翻过的车（都记下来，别再犯）

1. **改变被测物**：`screenProbe` 自己产出 70–190ms 长帧；
2. **读错顺序**：日志有多路写入者，`grep` 出来的行序**不是时间序** ⇒ 必须按时间戳排序
   （`awk` 取时间戳 + `sort -n`，命令在 `docs/量尺代价表.md`）；
3. **计数跨拍累积**：`直播新帧 8` 是攒出来的（10fps 的窗不可能一拍交 8 张）⇒ 已改成每拍取走；
4. **打点打在错的路径上**：`lastHoverMark` 只在指针 hover 打点，而用户的复现是**键盘 Tab**
   ⇒ 前几轮量到的长帧全是指针那一路，**没覆盖用户报的那一下** ⇒ 已补 `moveApp` / 窗口选中；
5. **旧构建在屏幕上**：用户按了 55 次 Tab，日志里新加的计时器 0 行 ⇒ 那个进程没有新代码。
   ⇒ 已补 `Tools/run.sh`：**停干净 → 起新构建 → 自证"进程启动晚于二进制 mtime"**。

- `LivePreviewPool`：**只把当前显示组的帧交给主线程** + 换回来时补一帧；

## 2026-09-22 追加:hover 到底掉不掉帧(用户报「我感觉 hover 还有点掉帧」+「60Hz 是不是没办法 0 损失」)

工具:`Tools/SmokeHover.swift`(**新**;它自己也踩了两个坑,写在文件头 ✓)

### 先说两个方法论事故(都是被用户当场指出的)

1. **第一版扫描线是猜的** ✗ —— `union.minY + 42` 那种。用户看着屏幕说:
   「我看着你指针根本没扫到, 没hover到app」⇒ 他完全说对了 ✓
   实测几何:环面板窗口 1259x375@330,368(图标行在窗口高度的 0.45–0.72)、
   托盘窗口 976x377@471,176(卡片行同样)⇒ 我原来那三条线全在空白区 ✗ ⇒ 量了一轮空气 ✗
   ⇒ 教训:**量之前先看一眼实物**(`screencapture -l<windowid>` 抓窗口本体,别裁全屏 ✗)
2. **12px 步长连续横扫 ≠ 人 hover** ✗ —— 每秒几十次 hover-in/out,
   量到的是**卡片边界抖动**,不是人感受到的 hover ✗

### 结果(60Hz 外接屏,步长 8ms ≈ 真实触控板事件率)

| 场景 | 帧数 | P50 | P95 | max | 长帧 | 起流 |
|---|---|---|---|---|---|---|
| **面板开着、指针不动**(基线) | 870 | 16.7 | **16.7** | 24.3 | **0(0%)** | — |
| **人那样 hover**(6 步挪进去 + 停 12s)×3 遍 | 765×3 | 16.7 | **16.7** | 22.2/27.0/19.2 | **0–1(0%)** | 3–4 次 |
| 连续横扫图标行 | 421 | 16.7 | 17.6 | 32.0 | 9(2%) | 2 |
| 连续横扫卡片行 | 494 | 16.7 | 21.0 | 44.4 | 15(3%) | 4 |
| 连续全扫 | 982 | 16.7 | 18.4 | 41.6 | 27(3%) | 5 |

**直播开 vs 关(卡片行连续横扫,各两遍)** ⇒ **关掉反而更差** ✓:
`开: P95 20.4/17.5 · 长帧 13(3%)/8(2%)` · `关: P95 21.5/20.7 · 长帧 15(3%)/18(4%)`
⇒ **掉帧与我们的直播流无关** ✓(这一条把"live preview 是掉帧来源"彻底排除掉了 ✓)

### 结论

- **人真的 hover:** 0 掉帧 ✓(3 遍 12s,含冷启动起流 ✓)——用户感觉到的"hover 掉帧"没量到 ✓
- **只有"连续快速跨卡片边界"才会掉**(2–4%);那是 hover 状态与动效的 churn,不是取流 ✗
- **60Hz 与"0 损失":** 我们能控制的部分**在预算内** ——
  60Hz 预算 16.7ms,实测 P50 恰好 16.7(= 每拍都赶上 ✓)、我们每次按键/悬停的活 < 2ms ✓;
  但只要有一拍晚到,60Hz 上就是 **16.7ms 的洞**(120Hz 是 8.3ms)⇒ 观感更明显 ✓。
  最后一帧的合成归 WindowServer/合成器管,App **没法承诺**绝对 0 损失 ✗;
  能说的是:**我们不是瓶颈** ✓(面板开着不动 = 0 长帧 ✓,人那样 hover = 0 长帧 ✓)
