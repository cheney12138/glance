# 排查记录:多窗口 App 的第二张卡"要点两遍"(实为永远点不着)

2026-09-19 · 耗时一个上午 · 现已修复,修复手段 = **合成器闸**(`PanelController.updateStripClickGate`)

## 症状

从 A 应用切到 B 应用后唤起面板,指针去点多窗口 App( IntelliJ IDEA 最典型)的第二张/后面的卡片,第一次点击无响应;有时点两三次也不行。单窗口 App 的卡片、以及托盘**上排**的卡片一直好使 —— 所以"时好时坏",极难稳定复现。用户补充线索:点击打不开时"环会变色,会变得浅一点"(长条玻璃失去事件响应的观感)。

## 真因(两层叠加)

1. **吞击主因 —— z 序 × 呼吸区重叠**:托盘被故意压一层(`popUpMenu - 1`,demo 让长条盖住托盘阴影尾,防"黑影"),而长条整窗框带 108pt 透明呼吸区,与托盘玻璃大幅重叠(实测盖进玻璃 ~185pt)。落在这条带的点击被 WindowServer 送进**长条**;长条 `ClickThroughHostingView.hitTest` 在呼吸区返回 nil,AppKit **不转发**,事件就地落地。一锤定音账:`z序=长前托后 长hit=nil 托hit=ClickThroughHostingView`。
   - 托盘**上排**卡片在长条窗框之外 → 一直好使;单行托盘的玻璃整体在带外 → 也好使;只有"带 ∩ 玻璃"那一角死 —— 这就是"时好时坏"的来源。
2. **诊断干扰 —— 托盘窗口 ≠ 托盘玻璃**:托盘窗口按"整局最大布局"开,玻璃只是贴底坐在大窗口里。窗口帧 (249,544,1478,950) 里单行组(如 IDEA 4 窗)的真实玻璃只占 y≈[700,870],下方 ~156pt 是**空的**。修复验证期间曾误把点击打进空区,造成"还是没修好"的假象(截屏对齐视觉位置后澄清)。

## 排查弯路(避免重走)

| 弯路 | 为何错 |
|---|---|
| key 分配吞击(托盘 `keyable=false`、`becomesKeyOnlyIfNeeded`) | key 变化日志全程零记录,两扇窗从头到尾没当过 key |
| 卡片间隙命中空洞(行级 `SpatialTapGesture` + `cardTapped`) | 那是另一层问题(间隙确实曾是洞),但不是本 bug 主因 |
| `sendEvent` 重建事件同位转交 | 合成 NSEvent 进了托盘、`mouseDown/Up` 都到了宿主视图,但 **SwiftUI 手势不认**(down/up 双双无声)—— 别再走回头路 |
| 托盘翻到长条前面的 level 实验 | 点击送达不是问题的全部;且与黑影防线冲突,已还原 |

## 修复:合成器闸

60Hz 帧拍本来就每帧采样指针,顺手翻闸:**指针进托盘玻璃时长条 `ignoresMouseEvents = true`**(WindowServer 整窗跳过,点击落到下层唯一的自家窗 = 托盘,真实事件原路进 SwiftUI),离开玻璃即还原。

- 两窗 z 序、视觉、黑影防线**一字不动**;
- 副作用审视:闸开期间长条收不到鼠标事件 —— 指针在托盘玻璃里本来就轮不到长条;翻闸 ≤16ms 帧拍延迟,极快的"划出即点"理论上可吞一下长条点击,实测窗口足够大;
- hover 不受影响(长条/托盘选中都是帧拍几何算的,不靠事件);
- 验证:AppKit (728,717) —— 长条窗框罩住的死区带 ∩ 真实玻璃下缘 —— 修复前必死,修复后 `win=托 → 确认` 一次即中;用户实机复验通过。

## 遗留备案

- **托盘"玻璃下方隐形空区"**:窗口比玻璃大,"面板外点击判据"用的是窗口框,该空区点击不关面板。用户裁定**不处理**(缝隙太小,没人会去点)。
- **关闭后误触闪现**(同日上午):点卡片关面板后 0.72s,手挪动时三指刷触被照章唤起(数据上与真点无法区分)。方案 A"关闭后 0.8s 静默窗"已提出,**挂起** —— 误触频率高了再做。
