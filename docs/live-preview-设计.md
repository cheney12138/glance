> 这份文档的第一读者是**下一次要动这块代码的人**（很可能就是我自己）。
> 前半是**昨天踩过的坑**（每一条都带实机病例），后半是据此定下的设计。

## 0. 目标与验收标准

用户口径（原话）：

> "就是想要 **expose 的原生体验**"、"别人不一定看得出来，但我知道这个问题存在就会很难受"

| # | 验收项 | 判据（可量） |
|---|---|---|
| G1 | **画面是活的** | 托盘每张卡都在出帧，不是静图 |
| G2 | **零切换感** | 从"没有画面"到"有画面"只发生**一次**（首帧），此后**永不换源** |
| G3 | **任何时刻都不空** | 卡片的源只有 live；没帧时显示**静默态**（不是深色块、不是 loading 文案） |
| G4 | **不抖、不缩、不糊、不位移** | 采样率/裁切/内容框/尺寸/取数来源**全部同源**，且**整局冻结** |
| G5 | **不掉帧** | `[帧]` 探针：长帧 ≤2%、无 1-4s 区间的持续长帧 |
| G6 | **成本可接受** | 选中 1 条按档位 + 其余 5fps；面板关闭 ⇒ 0 条流 |

## 1. 昨天的坑（16 条，全部实测）

### A. 结构类（最贵的三条）

| # | 现象（原话） | 真因 | 现在成为 |
|---|---|---|---|
| A1 | "景深、错位、按钮画了两遍" | **共享一块 CALayer + 零拷贝 IOSurface** ⇒ 归属靠共享标量猜，多线程串台（日志 `⚠️ 归属为空` ×79） | **禁止共享可变资源**：每扇窗**自带一帧**（`frames[wid]`） |
| A2 | "空白期 / 黑窗 / 缩小" | 展示层做成"**快照当主力、live 事后替换**" ⇒ 任何时刻两个源都可能不一致 | **单一数据源**：快照**整条退出**展示链；兜底只能是"没有数据"的占位 |
| A3 | "还是有放大" | live 的裁切依赖**快照的中间产物**（裁切分数）⇒ 局中重拍一次 ⇒ 画面缩放一次 | **不跨源**：裁切由本流首帧自己算一次并冻结 |

### B. 几何/采样率类（同一族，追了 6 轮）

| # | 现象 | 真因 | 现在成为 |
|---|---|---|---|
| B1 | "底部一条白边" | 流缓冲比例写死 1.6 ⇒ `scalesToFit` fit 出透明条 | 缓冲比例 = **窗口实时比例**，`scalesToFit = false` |
| B2 | "被撑了一下" | live 自己扫透明边 ⇒ 扫出**不对称**矩形（只切右下 6×4px） | 两条路**同一把尺子**（或不需要尺子 —— 单一源时不存在） |
| B3 | "缩小" | 干脆不裁 ⇒ 圆角尾巴参与 `.fill` | 同上：**裁切规则唯一** |
| B4 | "变模糊" | 快照 720px 清晰 ⇄ live 244px 被放大 **1.86×** | 出图 = **卡片绘制尺寸 × 屏倍率**（1:1） |
| B5 | "轻微放大" | 快照用 `w.bounds`（枚举口径）⇄ live 用 `SCWindow.frame`（SCK 口径，含阴影） | **取数来源也要同源**（不只是公式同源） |
| B6 | "还是有放大" | 两条路对同一窗取的**内容框**可能不同（一含阴影一不含） | 两条路都显式 `ignoreShadowsSingleWindow = true` |

> **B 族的教训一句话**：只要存在两个源，就要在**几何 / 裁切 / 采样率 / 取数来源 / 内容框**上无止境地互相追平 ——
> 每对齐一个，就冒出下一个。**根解不是"对齐"，是"只有一个源"**（B1…B6 在单一源下全部不存在）。

### C. 时序/触发类

| # | 现象 | 真因 | 现在成为 |
|---|---|---|---|
| C1 | "截图要 560–660ms 才上屏" | 快照走 `SCScreenshotManager`，与流抢 SCK，且每局批量重拍 | live 是唯一源 ⇒ 快照不再进展示链 |
| C2 | "卡片空着好几百毫秒" | **延迟叠加**：起流推迟 150ms + 池防抖 120ms + 首帧 ~150ms | 首轮**零延迟**对账、起流**零延迟**；首帧实测 **36–74ms** |
| C3 | "局中一闪" | 分档换帧率时**重启流**（30↔5fps） | 换档**保留上一帧** ⇒ 重启不可见；帧**跨会话保留** |
| C4 | "CatPaw 上出现左滑入场" | IDE 的窗口集合在开场几帧刷新 ⇒ SwiftUI 判成"插入"⇒ 播 `x:+14` 位移 | 位移量 token 化（`segmentNudge = 0`）；**入场无动效** |

### D. 我踩的纪律类（这三条最该记）

| # | 事故 | 真因 | 现在成为 |
|---|---|---|---|
| D1 | **三指四指全失效、且一条日志都不留** | 掌缘搭在板上打字 ⇒ "按压账本"收口帧永不到来 ⇒ 账本撑开 **49 分钟** ⇒ 之后所有触摸被吸进毒账本 ⇒ 判卷永远失败（判卷不跑 = 沉默失效） | 账本 **1.0s 未收口 ⇒ 整本作废重来** + 自愈打一行日志（`stuckLedgerAfter`） |
| D2 | **面板整块空白**（看起来像"三指换不起来"） | 我为了治 1px 抖动把**窗口框**单边取整 ⇒ 与 `PanelView` 的 padding **两套尺寸账不一致** ⇒ AppKit 布局递归 ⇒ 画不出来（**你们 T6 病例早就写过这件事**） | **尺寸是多方的账**：窗口框 / 内容尺寸 / padding / 卷动区，要么**一起改**，要么**不改**；`[上屏探针]` 全 0 ⇒ 立即告警 |
| D3 | 诊断开关污染验收 | `debug.livePreviewOnly` 忘了复位 ⇒ 用户看到一个**不存在的 bug**（空白期） | 诊断开关**必须**：① 启动时自报状态；② 交付前复位；③ 把它造成的现象写进说明 |

## 2. 设计（从上一条结论直接推出来）

### 2.1 一句话

> **一扇窗一条流、一张帧；卡片只有这一个源；出图规格首启冻结。**

### 2.2 不变量（改代码前先对照）

| # | 不变量 | 为什么 |
|---|---|---|
| I1 | **展示层只有一个源**（live）；快照**不进**托盘 | A2 / B 族的根解 |
| I2 | 每扇窗**自带一帧**（`frames[wid]`），不共享任何可变渲染资源 | A1 |
| I3 | 出图规格（高度、比例、裁切、内容框）**首启算一次即冻结**，整局不变 | A3 / B5 / C3 |
| I4 | 无帧时显示**静默态**（淡 App 图标 / 底色），**不许**深色块、不许 loading 文案 | G3 |
| I5 | 单帧绘制**不做体外的活**（图标查找、文件、锁、`NSRunningApplication` 等一律缓存或预先算好） | D2 的孪生风险：view body 里的副作用会拖住渲染 |
| I6 | **不碰尺寸账**：任何布局/尺寸改动必须把窗口框、内容尺寸、padding 一起看 | D2 |
| I7 | 每条诊断日志**带时间轴**（`glog`），否则无法与 `[打卡]`/`[直播]` 对齐 | 昨天多次读到旧构建的数 |
| I8 | 诊断开关：启动自报 + 交付复位 | D3 |

### 2.3 数据流

```
 窗口集合(每局枚举)
      │
      ▼
 StreamPool.reconcile(可见窗口, 选中wid)        ← 对象池:声明"要哪些",不问"怎么开"
      │   · 每扇窗:SCStream(filter=desktopIndependentWindow)
      │   · 配置**首启冻结**:高 = 卡片绘制高 × 屏倍率;宽 = 高 × 窗口实时比例;
      │                     scalesToFit=false; ignoreShadowsSingleWindow=true
      │   · 帧率:选中 = 用户档位 / 其余 = 5fps(换档只重启那两条,帧保留)
      │   · 错峰 40ms 起流(避免向 WindowServer 打并发)
      ▼
 frames[wid] = CGImage        (VTCreateCGImageFromCVPixelBuffer,在流自己的队列)
      │   · 计数上限 10(长期会话不涨内存)
      │   · **跨会话保留**(面板关了也留着)⇒ 下一次唤起第一眼就是 live ⇒ G2
      ▼
 WindowThumb(卡片)
      │   if let f = frames[wid] → Image(f)         ← 唯一的一支
      │   else                   → 静默态(淡图标)   ← 唯一的一支
      ▼
 「座」= 应用级毛玻璃:用**该窗第一张可用帧**做一次性底面(缓存,不逐帧重算)
```

### 2.4 与快照的关系（明确划清）

- **实时预览开启** ⇒ 快照**完全退出**：不采集（省 SCK 争用）、不绘制、不被依赖。
- **实时预览关闭** ⇒ 快照链**原样工作**（当前已提交的行为），两块能力**互不影响**、可单独调试。
- **托盘不再有"截图填充"**：`thumb(at:)` 不再把 `snapshotter.cache[wid]` 传进卡片。

### 2.5 成本账（实测）

| 项 | 数字 | 来源 |
|---|---|---|
| 单条流 | ≈2%/s @10fps；≈5%/s @30fps | 三次 `ps` 采样（3 条 30fps = 11.6–17.9%，基线 2.2%） |
| 单帧像素 | 0.11–0.13 MPix（446×244 ~ 490×293） | `[直播] 几何核对` |
| 首帧 | **36–74ms** | `[直播] 首帧` |
| 面板关闭 | 0 条流 | `[直播] 全部停流` |
| 代价 | 面板打开期间录屏标识常亮（macOS 规则，DockDoor 同样） | 实测 |

## 3. 验收探针（每条不变量配一条账）

| 不变量 | 探针 | 合格读数 |
|---|---|---|
| I1 | `[直播] 模式 快照=关` | 无 `[T5] 预截` |
| I2 | 每帧自带 wid + 代号 | 无 `归属为空` |
| I3 | `[直播] 几何核对 wid=… 帧=WxH 期望=Npx`（一次性） | 帧高 = 期望；整局只出现一次 |
| I4 | 目视 + `[位移] 卡片` | 同一 wid 只在"静默态→live"出现**一次** |
| I5 | 帧探针 `[帧]` | 长帧 ≤2%，且不落在 2-4s 区间 |
| I6 | `[位移] 面板框 … (已上屏)` | **不出现**（或只出现±1px） |
| I7 | 所有新日志走 `glog` | 行首都有 `[ Nms]` |
| I8 | 启动行 `[诊断] livePreviewOnly=开` | 交付时无此行 |

外加一条**兜底告警** ✓：`[上屏探针]` 连续 ≥3 帧全 0 ⇒ 打一行红字（`面板疑似空白渲染`）—— D2 若再犯，一秒定位。

## 4. 实施顺序（每步都能单独验收 / 单独回退）

| 步 | 内容 | 验收 |
|---|---|---|
| **S1** | 只建池 + 起流 + `frames`，**不改任何绘制**（卡片照旧显示快照） | 日志：`起流池 +=`、`首帧 36-74ms`；画面不变 |
| **S2** | 卡片改为"**live 优先**"，快照只在无帧时暂留（此时仍是两源，只是顺序变了） | 目视：卡片是活的；无空白 |
| **S3** | **摘掉快照**：`thumb(at:)` 不再传图；静默态 = 淡 App 图标；「座」改用首帧缓存 | 目视：任何时刻都不空；换源感消失 |
| **S4** | 分档帧率 + 错峰 + 首轮零延迟 + 帧跨会话保留 | `[帧]` 长帧 ≤2%；唤起 ~120ms 内即 live |
| **S5** | 快照链在 live 开启时整体退出 + 探针补齐 + 交付前复位诊断开关 | I1/I7/I8 全绿 |

> 纪律：**一步一提交、每步都能验收**；任何一步验收不过 ⇒ 只回退这一步（不推翻前面的 ✓）。

## 5. 明确**不做**的事（昨天的坑都长在这些地方）

1. ❌ 共享 CALayer / IOSurface 零拷贝（A1）；
2. ❌ 快照当主力、live 事后替换（A2）；
3. ❌ live 依赖快照的中间产物（A3）；
4. ❌ 为"省一点成本"砍流数（应该砍**帧率**，C）；
5. ❌ 入场/换源动效（C4）；
6. ❌ 单边取整 / 单边改尺寸（D2）；
7. ❌ 在 view body 里做有副作用的活（I5）；
8. ❌ 不带时间轴的日志（I7）。

## 附录:S3/S5 落地(2026-09-24,换源位移的收口)

用户实报「live 开着,预览窗有一个轻微位移,乍一看像抖动」。当日 `20b3253` 已把 live 缓冲的
**尺寸公式**改成与快照同函数,但换源重排仍在 —— 因为"同源"只做到了公式,**输入**仍各算各的:
卡片盒用 `record.bounds`(CGWindowList),live 缓冲用 `SCWindow.frame`(SCK),两口径对同一扇窗
可差零点几 pt ⇒ 图拉伸进盒 ⇒ 换源那一下整幅重排。B 族教训再次应验:"一切"永远比你想的多一项。

本轮收口(3 文件):
- **A · 输入同源**:卡片盒随 `sync` 传入池(`PanelController.updatePreview` 算好),`start()` 直接
  用它出像素规格,不再从 `SCWindow.frame` 重算;
- **S3 · 快照退出展示链**(当晚再收口,见下):`thumb(at:)` 在 live 开时传 `image: nil`;「座」的源
  改为"该窗第一张可用 live 帧"(`SeatImageCache.seat(wid:cg:)` 新入口,与快照同一本缓存账)。

**当晚二次收口(S2''/S5',用户实报「刚开始有 loading」)**:S3 的静默图标只闪 ~200ms,但用户要
**无感**。live 首帧有系统级下限(建流到首帧 36–74ms,压不成零),于是回到"快照垫图"——但这次
与 S2 有本质不同:**两个源已按构造同尺**(A 修之后同一函数、同一输入、同一盒子),垫图→换源
几何不动,当年 B 族的"换源重排"不存在了。口径:
- 冷窗(还没有任何 live 帧的窗)垫一张新鲜快照,live 首帧到了自动退场;
- 货源 = S5':`Snapshotter.precapture` 只在**面板在台上**(流在跑)让位;面板关着
  (收场即 stopAll ⇒ 0 条流)照常采 —— 无 SCK 争用,又总有垫图。冷启动 sweep(启动 2.5s)负责
  App 刚起时的第一份货;
- 接受面:开 App 后 2.5s 内就唤起、或窗口开出来还不到 5s(开窗扫一轮都没到)⇒ 那张卡仍闪
  一下静默图标(没垫图可垫);垫图内容是"上一眼"的旧画面,换源那一下内容会刷新 —— 是刷新,
  不是位移。
- 顺带修了预热目标尺寸的 `max/min` 笔误(原来预热出的图与渲染键对不上,整批白算)。

> ⚠️ **S2''/S5' 已于次日退役(2026-09-25,用户裁定「回到上一版,loading 显示 App 图标能接受」)**:
> 垫图只对齐了**几何**(盒子/比例),没对齐**内容画幅** —— 快照走 `transparentTrimRect` 裁过
> 透明衬边、live 不裁 ⇒ 换源那一下内容仍会"移一下",用户实报抖动复现。
> ⇒ 冷窗回到 S3 的**静默 App 图标**;live 开 = 快照**不采也不显示**(I1 彻底成立);
> CardImageCache 预热随之只在 live 关时执行。**教训补进 B 族:"一切属性同源"里还有一项叫
> 内容画幅(裁切原点)—— 两个源对齐到最后,差的永远是你以为不算事的那一层。**



**同晚第三口(用户实报「冷启动遮罩后置渲染」)**:那块遮罩(红绿灯下的毛玻璃「座」)是**后台异步**
算的,没算好就整层不画 —— 冷启动那一局**没人触发它**:`updatePreview` 的预热跑在上屏那一拍,
而快照还在后台拍 ⇒ 预热空转;publish 只写 cache,无后续钩子 ⇒ 座要等下一次换 app 才被现算
⇒ "卡面先出、遮罩迟半拍浮上去"。修:`PanelController.init` 常驻订阅 `Snapshotter.$cache`,
图一落账就把那扇窗的座在后台算掉 —— 冷启动 sweep(启动 2.5s)拍完图就在没人看的时候把整环
的座算热,顺带付掉 CIContext/shader 首编译(冷启动首张 blur 慢一截的来源 ✓)。判问走
`SeatImageCache.cached`(只查不算,不维护第二本 wid 账 —— 换屏 reset 后自记账会对不上 ✗)。

## 附录:hover 卡顿的排查(2026-09-21,结论)

**症状**:用户实报"live 开着时 hover 不流畅";量到的现象是**换卡/换 app 那一拍偶尔 20–40ms**(整局 P50/P95 都是 16.7ms ⇒ 平均账看不见它 ⇒ 所以专门加了 `[悬停拍]`:悬停后 200ms 内**每一拍**单独记一行)。

**查法(一次一个变量 + 结论留档)**:

| 轮 | 变量 | 丢拍率 | 结论 |
|---|---|---|---|
| ① | 基线 | 12/506 = 2.4% | — |
| ② | `debug.plainCard=1`(选中态的环/浮起/阴影全不下) | 4/158 = 2.5% | **选中装饰不是真凶** ✗ |
| ③ | `debug.opaqueTray=1`(托盘不用 Liquid Glass,换纯色) | 16/651 = 2.5% | **玻璃背板重采样不是真凶** ✗ |
| ④ | 只开 `debug.trace`(关掉**上屏像素探针**) | 17/385 = 4.4%,**大停(>60ms) 0 条** | 70–190ms 的大停**是探针自己造成的** ✗ |

**教训(必须记)**:

## 附录:关面板卡顿 = 探针自己的 O(n²)(2026-09-24,量具污染被测物第三次)

**症状**:用户实报「点击空白处关闭面板,有时候响应很慢,还出现了指针 loading」。

**日志铁证**:`[T6] …:面板关闭` → `[T6] 收场` 之间的空窗 = **帧数 × 0.7ms 严格线性**
(334 帧 → 246ms / 2516 帧 → 1749ms / 3324 帧 → 2367ms;2.37s 那次就是 BeachBall)。

**真因**:`FrameProbe.stop()` 里 `longFrame`/`cadenceMs` 是**计算属性**,每取一次 =
`suffix(240)+filter+sorted` 一整套(含数组分配);它们被直接写进了 `intervals.filter` 与
直方图 `for` 的**逐元素条件**里 ⇒ n 帧 = 2n 次"240 帧排序",Debug 下 ≈0.7ms/帧 ⇒
关面板时主线程同步卡 0.2–2.4s。**trace 不开不犯**(stop 提前 return)⇒ 又是"量具自己造成的卡"。

**修**:两个值各算一次存本地,闭包只读常量。

**教训(进规矩)**:计算属性里只要藏了"超过 O(1) 的活",就**不许**出现在逐元素闭包的条件里 ——
编译器不会提醒你它每帧重算;Swift 的 `filter/for` 写得越自然,这个坑越隐蔽。

## 附录:窗口变形 ⇒ 重启流(2026-09-25,I3 的补丁)

**症状**:用户实报「调整窗口尺寸之后,⌘Tab 唤起,卡片有黑边」(实测:窗被压矮后,
画面只占卡的上半,下半一条黑)。

**真因**:I3「出图规格首启冻结」只管住了"局中不许变" —— 但**窗口真的会变形**:
冻结之后窗被拉高/压扁,流仍按旧规格向 SCK 要帧,SCK(`scalesToFit=false`)
把变小了的窗口铺进旧缓冲 ⇒ 空出的部分就是黑边;变大则被拉伸。
而 `sync` 的"名单没变就早退"把"盒子变了"也一起挡掉了 ⇒ 永远没人重启那条流 ✗。

**修(两处)**:
- `sync` 早退之前先比盒子:名单没变但盒子变了 ⇒ 放行;
- `reconcile` 的 starts 轮(新建流是系统级重活,只许在这一轮):已在跑的流,
  冻结规格与当前盒子差 >2px ⇒ **重启**(与换档同一手法,`latest`/帧盒不动 ⇒ 不闪 ✓)。

**I3 补丁**:冻结防的是"局中源自己变规格"(A3 的画面忽然缩放),不防"用户真的改了窗口" ——
后者必须有人重启,且只能在 starts 轮,帧保留。

**同日附一条小窗可见性**:窗口缩得比红绿灯胶囊(自然宽 ~61pt)还小时,整组灯 + 雾檐
**不画**(`PanelMetrics.thumbLightsMinW/MinH`)—— 被卡缘裁掉一半的灯既不能看也不能点,
不如没有;关窗走 W 键。
