## 过程中揪出的两个真 bug(均已修)

1. **悬停回退单误杀段**(用户实报「白名单的 App 没办法启动」的主因):
   回退单是"入口槽 + 悬停预览"时代的语义(指针离开启动区 0.12s = 收段)。模型 C 里
   段只能由 ↓/四指/Tab **主动**进入,指针不在面板上与段的生死无关 —— 但回退单仍在,
   四指唤起后指针不在面板上 ⇒ 段 0.12s 内静默退回主环 ⇒ 永远来不及确认。
   日志证据:段内选中 → 半分钟后主环选中 → 确认,中间无任何段操作。
   **修:回退单机制整段退役**,段保持粘性,由 ↑/Tab/Esc/3s 闲置收场。

2. **↓+Tab 从段尾绕回主环**:`launchIndex == nil`(↓ 刚进段还没选)时,Tab 的兜底
   `cur = n-1` 直接把人推出段 —— 键盘流选不中白名单 App。**修:nil = 站在段门口**,
   正向 Tab 从第一格进,反向 ⇧Tab 从最后一格进。

## 附:Pearcleaner「无法启动」排查(2026-09-19,已修复)

用户实报白名单里的 Pearcleaner 启动不了。排查链(逐层排除):

| 启动方式 | 结果 |
|---|---|
| Glance 面板确认(`[T83]` × 2) | `openApplication` 回调成功,无"启动失败"日志 |
| 相同 API 直调(swift 探针) | 回调成功发放 pid,进程瞬间消失 |
| 系统 `open -a Pearcleaner`(终端里) | 同样秒退 |
| **Spotlight(用户实测)** | **正常启动** ← 关键差异 |

**真凶**(读 Pearcleaner 4.4.3 源码 `Logic/Logic.swift handleLaunchMode`):
`TERM` 环境变量非空且非 `dumb` ⇒ 判定"从终端启动" ⇒ 打印 CLI 帮助后 `exit(0)`。
而 Glance 进程环境里有 `TERM=xterm-ghostty`(开发期反复用 shell `open` 拉起 Glance 带入),
`OpenConfiguration.environment` 会**并入**当前环境 ⇒ Pearcleaner 继承到 TERM ⇒ 闪退。
Spotlight 的环境干净,所以用户那边秒启动。

**修复(两层)**:
1. Glance 启动其他 App 时净化终端语境:`cfg.environment = ["TERM": "dumb"]`
   (对 GUI App 无意义,对 Pearcleaner 这类自检等于"不在终端");
2. 开发期注意:shell 里 `open` 拉起的 Glance 会继承终端环境 —— 本次已用
   `env -i open` 干净重启。

**复验**:`[T83] 启动 Pearcleaner` → 进程存活 ✓(↓ → Tab×3 → Enter 全键盘流)
