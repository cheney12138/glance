# ADR-0011:保留「预截」,不改成"悬停才拍"

**状态**:已采纳(2026-09-16,设计评审)
**相关**:`CONTEXT.md`(预截 / 卡面 / 卡壳)、README「Instant, because nothing is captured on the way in」、`Inventory/Snapshotter.swift`

## 背景

评审"有用户不喜欢预览窗"时,对照了 LumaRing 的做法:它的列表**只有静态 App 图标**,
**图片只在悬停某个窗口时弹出**(它自己的设置原文:「悬停窗口时展开大预览」,
并注明"最小化窗口暂不提供图片预览")。这条路的直观好处是省一次抓图。

## 决定

**保留预截**(面板出现前就把本屏窗口全部拍完,展开层只显示现成图)。
**不采用**"悬停/选中才拍"。

## 为什么

性能**不是**我们的瓶颈,数字是现成的:

- 一整局唤起实测 **24.7ms**(枚举 13.3 · 落点 0.1 · 开窗 4.8 · 首帧 6.5);
- 抓图**不在主线程**(早期就是为帧率把它挪出去的);
- 每局要拍的窗口数通常 **1～2**(`[T5] 预截 要拍 N 窗`),个别 App 5～10 扇。

即:**换成"悬停才拍"要付出确定的手感损失**(从"进来就是现成的"→"要看才给你"),
去换一个我们这里**并不存在**的性能问题。

## 后果

- 卡面要统一,只能在**"图已经在手里"**这个前提下做(见下一轮:统一底色 / 只让选中的那张恢复原样),
  不能靠"少拍图"来减负。
- 若将来某个平台(例如窗口数极多、或抓图变慢)让这条账反了,重新评估的判据是:
  **整局唤起(P95)是否被拍图拖过一帧预算** —— 超过才谈这条路 ✗。
