# ADR-0009:入口按操作对象分(窗用 ⌥,屏用 ⌃,⌘ 不新增)

**状态**:已采纳(2026-09-15,用户裁决;键位本身由实现方设计)
**相关**:ADR-0005(接管系统切换器必须显式开启)、ADR-0007(原子操作)、`CONTEXT.md`(指针场景 / 键盘场景)

## 决定

产品有且只有**两个入口**,按**操作对象**分工 —— 不是按功能清单分工:

| 入口 | 对象 | 内容 |
|---|---|---|
| **⌥**(按住) | 一扇**窗** | 面板:选 App、选窗、处置窗(`Q/W/M/F/H`)、`` ` `` 组内循环 |
| **⌃**(双击) | 一块**屏** / 指针 | 指针跨屏(将来"把窗口送到另一块屏"也归这里) |
| **⌘** | — | **不新增任何功能**,只留给"接管系统 ⌘Tab"这个开关 |

判决规则(以后加功能的唯一标准):**它动的是窗,还是屏?** 答案唯一。
**永远不往 ⌘ 上加功能** —— 那必然和系统或其他 App 打架。

## 否决的方案

- **单入口**:把屏幕级动作硬塞进窗口级面板,正是多屏语义做不好的地方。
- **前缀/分层入口**(先按 leader 再按字母):功能可无限扩张,但必须被用户学习 ✗,
  违背"不训练用户"的既定纪律;而且它会让"这个功能放哪个键"变成审美争论。

## 后果

- 用户原话:「快捷键这块你先设计吧,我觉得更重要的是**入口/方式**,快捷键只要顺手、有效率就行。」
  ⇒ 键位是实现细节,可随实机手感调整;**入口的分工轴**才是这份 ADR 要守的东西。
- 「吞键必须显式开启」(ADR-0005)升格为**全局规则**:将来任何吞键都遵此办理,默认一律不吞。

## 键位的可配置边界(2026-09-15 补充,用户裁决:选 (b))

- **触发键可改**(⌥/⌘ 之类):它在别人机器上冲突概率最高,不改就没法用 —— 已有「触发键」录制入口。
- **面板内的单字母键固定**(`Q/W/M/F/H`、`` ` ``、`←→↑↓`、`⏎`):它们**不是独立快捷键** ✗,
  只在面板打开期间存在,不占用系统任何键位;改成每人一套只会让"按文档学的键位"在别人机器上失效。
- **⌃⌃(双击)不可自定义**:它没有键位可绑,只有"双击哪个修饰键"这一维;今天固定为 ⌃。
