# ADR-0006 窗口尺寸是「会话不变量」,不是「选中项的函数」

状态:接受(2026-09-15) · 起因:`[工] 托盘改尺寸 主线程 23.3ms`

## 决定

自绘窗口(长条 / 托盘 / 设置窗)的**尺寸**不许跟着"当前选中"这类**用户输入**变。

- 尺寸按**整局(或整组)的最大**算一次,开局 `setFrame` 一次,整局不再动;
- 内容在窗口里**自适应**:托盘是"底部对齐 + 水平居中"(小布局看起来与等尺寸时一个像素不差);
- 若某个场景**必须**按内容定尺寸(一次性浮窗之类),那就**在窗口可见之前**定好 —— 见下面 DockDoor 的做法。

## 为什么(病例 + 实测数字)

- 托盘每换一个 App,卡片数就变 → 窗口尺寸变。而 `NSWindow.setFrame` 在"内容是一棵活的 SwiftUI 树"
  的窗口上**是同步的**:整棵子树重排 + 后备存储重分配。实测:
  `[工] 托盘改尺寸 主线程 6.9ms / 7.2ms / 23.3ms`(窗口越小越便宜,卡片多时 20ms+)。
- 后果不是"慢一点",而是**输入延迟**:同一份日志里 `[工] 键盘换选中 主线程 26.3ms`,
  其中 `托盘改尺寸` 占 **23.3ms(89%)**。入场上浮只有 0.2s —— 用户在入场里按一下 Tab,
  就被这 23ms 压住,读起来是"上浮不流畅"(用户原话)。
- 修法后:窗口 732×406pt **整局只 `setFrame` 一次**,`托盘改尺寸` 从 23.3ms 降到 <2ms 不再单独记账;
  `[帧]` 长帧从 1–6% 降到 ~1%。

## 参考实现(两个都读过源码)

- **AltTab**:一局之内把所有窗排进**同一张网格**(`src/switcher/main-window/TilesView.swift`
  的 `updateItemsAndLayout`),尺寸在开局算一次,换选中只移动高亮 —— 尺寸从头到尾不变。
  他们的网格天生与"当前选中"无关,**是被结构救的**,不是靠优化。
- **DockDoor**:`DockDoor/Utilities/Window Management/SwiftUIWindow.swift` 的 `show()` 里
  `intrinsicContentSize` → `setContentSize(finalSize)` → **然后才** `makeKeyAndOrderFront`。
  同一笔同步布局开销,但发生在窗口**可见之前**,所以一帧都不丢。

**结论**:两种做法共享同一条纪律 —— *不要在"已经可见、且正在导航/动效"的窗口上改尺寸*。
尺寸要么冻结一整局,要么在亮相之前定死。

## 推论(已经踩过一次)

窗口**可能比内容大**(按整局最大开)。于是所有"指针/点击在不在里面"的判断都**必须用内容矩形**,
不能用窗口 frame。我们有三处(见 `docs/debugging.md` §11 的清单):指针重定位、面板外点击判外、屏幕边缘收边。
漏一处就是"点在托盘旁边的空白不关面板"这类慢性病 —— 不崩,但一直不对。
