# ADR-0012:不做「拖拽删除」——破坏性动作只留在键盘上

**状态**:已采纳(2026-09-16,实现后由用户裁决整条退回)
**相关**:ADR-0007(原子操作/不替用户决定)、ADR-0009(入口按操作对象分)、`CONTEXT.md`(指针场景 / 破坏性键盘操作 / 处决即散场)

## 背景

对标 LumaRing 时发现它能"拖拽 App 移除"(其语义经源码确认为**退出 App**),用户提出也要一个。
当天实现并落地了:窗口卡拖出 = 关闭窗口(`W`)、App 图标拖出 = 退出 App(`Q`),
阈值 60pt、越界后图标变灰、松手执行。

## 决定

**整条退回。** 破坏性动作(退出 / 关闭 / 最小化 / 全屏 / 隐藏)只由键盘在面板内触发,不提供拖拽路径。

用户裁决原话:「拉到吧, 这个拖拽删除的功能全部退回,**本质上已经围绕鼠标操作建立太多功能了**,
这个app设计是期望发挥快捷键操作的优势。」

## 为什么(以及当时否掉了什么)

1. **与产品主张相悖**。这个 App 的优势是"键盘操作的效率",指针场景的存在是为了**选择与确认**
   (hover 选中、点一下确认、双指滑动换组),不是为了把**处决**也搬过去。
   把 Q/W/M 也复制一份到拖拽上,是在自己最强的地方之外另建一套 —— 每多一套,就要多守一套边界。
2. **它引入的复杂度远大于它的价值**:拖动状态要管(抖动 ✗ / 窗口外松手收不到 onEnded ⇒ 状态残留 ✗ /
   面板关闭要复位 ✗),而"拖出面板"的观感还被 `ADR-0006`(窗口大小是会话不变量)截断 ——
   真要做成 Dock 那样,得为被拖物单开一个跟随窗口。
3. **实测证据**:实现当天即出现"疯狂抖动"与"拖完回不来"(图标停在偏移位置、原槽空着)。

## 后果

- **保留**:hover 选中、点一下确认、双指滑动换组、窗口卡上的红绿灯按钮 —— 它们都是**选择/确认**性质,
  与"指针场景"的定义一致。
- **不保留**:任何把破坏性动作绑定到拖拽/手势的提案。将来若有人提,先读本 ADR。
- **保留的一条技术资产**:`ClickThroughHostingView.acceptsFirstMouse` —— 它不是为了拖拽而加的,
  而是非激活面板的一般性正确设置(我们永远不是 key window),任何"按下并持续跟踪"的交互都需要它。
- 明确的 no 和 yes 一样值钱:**"键盘负责处决,鼠标负责选择"是这个产品的一条边界。**
